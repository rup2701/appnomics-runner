# Parking lot

Ideas worth keeping that are not being built now. Newest first. Move an item out when it becomes a change request.

## Product

- **Why a small business buys an AI builder (RP, Oct 30).** The build is one event; the need for changes lasts years. A restaurant owner today has to find a developer for every small change (menu, hours, a special, a photo) unless they already use a no-code tool. Because pages are metadata-driven, most changes are instant data edits, and only the occasional layout request is a Change run. The difference from Wix or Squarespace is saying the change in words instead of learning an editor. Check it with a real owner first: what was the last change, how long did it take, what did it cost, who did it. Pricing options: a monthly fee that includes changes, or a price per accepted change.
- **Chat changes after launch.** (1) "How do I change the hero image?" is answered from PROJECT_GUIDE.md, no build. (2) "Change the hero image" with an uploaded file is a data change: upload to the same route the owner area uses, set the field, show a draft, Publish or Discard. Code-level requests go through a Change run. Build order: the guide file, then image upload from chat after builder step 2.
- **Growth ladder for the waitlist site.** 1) Notify me of sign-ups, and send a confirmation to the visitor (Resend; one key, easiest). 2) More sections once the idea is validated (page blocks: pricing, how it works, FAQ, testimonials). 3) Text alerts (Twilio; needs carrier registration and opt-in consent, so later and small). 4) Subscriptions and payments (Stripe; changes the kind of site, handles money, so checked before shown; needs the owner's own account). Rungs 1 and 2 need only an email key; 3 and 4 need the owner's accounts.
- **Waitlist pack options still to add.** `look.hero_image`: background (today) or a framed product screenshot below the headline and button. An image slot on every benefit, with the designed placeholder only while the slot is empty. Both proven by a Change run on the DispatchOS demo first.
- **Deploy and owner-variable follow-ups.** Blob store creation is still a dashboard step for each site. Sign-in is not part of deploy verification. The first-deploy guard refuses an existing Vercel project name (added Oct 30 after a name clash overwrote a real project).
- **Morning loop (from Polsia's description).** Each morning the store's agent reads signups or orders, proposes two or three changes, and the owner approves them. Each approved change is a Change run. Fits "price per accepted change."
- **Post-build review.** The log's "Choices where the brief was unclear" become cards for the owner (keep or change, one click), and "Not verified" becomes "please check these." Each answer edits the brief and may trigger a Change run. The same questions feed the interview.
- **Fast preview path.** Draft the change and show it on a live preview in a minute or two; run the full checks only when the owner approves. Look and copy changes take the fast path; changes touching money, stock, orders or the database are checked before they are shown.
- **Preview design.** Two paths. (1) Data changes (order, show/hide, layout, text, colors): each block has a draft and a published copy; the signed-in owner sees the real site with a "Previewing draft" bar; Publish copies draft to live, Discard drops it. Instant, no rebuild. (2) Code changes: the agent works on a copy of the app with its own Neon branch if the database changes; a dev server with hot reload feeds a preview panel; only a quick type check runs while the owner looks; full build and e2e run on Approve (money, stock, orders and database changes are checked before they are shown); Approve merges and deploys, Reject deletes the copy. Cheap first version: a Vercel preview deploy per change (about 1 to 2 minutes, untested on our apps). Later: a container per customer with a dev server (the cloud worker). Also a `--fast` option on the Change job that skips e2e and ends with a preview deploy.
- **Card-count grid rule (site pack).** Grid columns follow the number of cards: 2 gives 2, 3 gives 3, 4 gives 2x2 (or 4 across), 5 or 6 gives 3. Never an orphan row. Add "no orphan rows" to the taste rubric. Ksandra's four benefits came out 3+1.
- **Project guide per app (from Figma Make).** The agent writes PROJECT_GUIDE.md into every app (structure, scripts, how to run, conventions, "start with task-relevant files") and the Change job reads it first instead of the whole log.
- **First live-preview test cases (Ksandra).** (1) Tighten the empty space above and below the content in the preview window. (2) Replace "Your answer appears here" with a short sample question and answer with numbered citations, labelled "Concept preview". Do these as plain-words requests once preview exists.
- **Tryglen-level product sites (later pack).** Numbered how-it-works steps, before and after panel, trust table, proof (logos, numbers, testimonials), alternating layouts. Needs interview questions and blocks for that material. Out of scope for the waitlist pack, where the bar is the polished first Ksandra build (full-screen hero, 2x2 benefits with icons, tools strip, HTML product mock-up). Get three tryglen screenshots (hero, mid-page, mobile) before writing exact type and spacing values.
- **Page blocks.** A page is blocks in an order (hero, preview, benefits, waitlist, footer). The owner shows, hides and edits them. First built for websites, reusable for store home pages.
- **Design controls (design mode).** Text styling, section styling and custom styling as data on each section: instant, no rebuild. Presets keep contrast safe. Custom styling goes through the Change job.
- **Select-a-section chat.** The owner clicks a section and says what to change; the assistant edits that section's data or starts a Change run.
- **Store memory.** An append-only log of changes and owner edits, so the brief and the live store do not drift apart. The shared assistant reads it.
- **Look presets by genre** (for example deep-tech or AI, DTC brand, gallery, editorial). Each is a font pairing, type scale, spacing, color roles and section patterns. The interview picks one; the agent adapts it.
- **Reference gallery with notes.** Screenshots of sites that do a genre well, with two or three lines on why. Learn principles, never copy a site.
- **Resume or personal site template.** Blocks: hero, about, experience, skills, projects, contact. The interview asks: is it mostly your story or mostly your work?
- **Iterate the interview** with the audience questions: who is it for, what do they do instead, where will you find them, what counts as success.
- **iOS and owner mobile app.** A separate pipeline (Xcode, simulator, review). A likely first app is the owner's phone app: orders and stock.

## Runner

- **Hosting decision (Oct 30).** Builder web app on Vercel with a hosted Postgres (Neon). Worker and runner together on Fly (Node, git, Chromium, a Postgres the runs can create databases on). First hosted version: one Fly app, builds share an environment. When strangers can start builds: a Fly Machine per build with only that run's secrets, destroyed afterward. Keep "run the build" behind one function in the worker so the host can change. Anthropic workspace spend limit is the hard cap. Verify current Fly and Railway pricing and limits before committing.
- **Screenshot tool.** Let the agent see its own Playwright screenshots, critique them against a short rubric, and fix the worst problems (one or two rounds).
- **Screenshots in the chat: the visual feedback loop (RP, Oct 31).** Big idea: the chat becomes the preview, so it stands in for a full preview/component-tree product until there are resources to build one. Loop: owner asks in words, the agent changes the site, the app runs, a screenshot comes back in the chat, the owner gives feedback. Two features on one capture step: (a) the owner sees the result; (b) the agent sees its own screenshots and critiques them (the entry above). Freshness guard: the build writes the git commit into the page (meta tag or response header); capture waits until the running site reports the commit that matches the repo's latest, so a stale page is never shown. **Moved to first item on the next list, right after the first hosted run works (RP, Oct 31).** Order: 1) at the Ready stage, desktop and mobile thumbnails of the live address (already published, so it cannot be stale; Chromium is already on the Fly image). 2) With chat changes after launch: request, Change run, preview deploy or rebuild, screenshots in the chat. 3) Agent self-critique, measured for image-token cost first. Not in the first hosted week.
- **Waiting message copy (RP, Oct 31).** "This might take a little while. Go grab a coffee ☕ We'll email you when your site is live." Show the email sentence only when `RESEND_API_KEY` is set; until then keep "You can close this window and come back."
- **Layout as data: a block list plus a renderer, across packs (RP, Nov 13).** Idea: a page is an ordered list of `{ block, variant }` plus tokens (fonts, colours, density), and a fixed component library renders it, like server-driven UI. Today `visibleSections`, `navLinks`, `footerColumns` and `page_plan` decide which blocks show, but order and look are fixed in the page files.
  - **Why:** layout presets (Operational Minimalist = today, Editorial Monograph = split hero, two-column story with drop cap, single-column menu, mixed-ratio gallery, Cinematic Dark Room, and so on) become data. Scout and the change planner edit a validated list, so "add From our menu", "move reviews up" and "switch look" need no model-written code. With stage two the list can live in the site database, so the owner could reorder or restyle from the admin with no rebuild (60 second refresh).
  - **Across verticals:** shared blocks (hero, story, gallery, reviews, hours and contact, call to action, footer) plus vertical blocks (restaurant menu, salon services, shop products). A pack = a content type (shared core plus vertical extension), a block library and presets. Swiss Grid and Kinetic Storyteller suit salon, studio and wellness packs more than restaurants.
  - **Cautions:** closed vocabulary and strict validation (no free CSS or arbitrary components); every block and variant must look right with real content and with placeholders; photo-led layouts (Editorial, Cinematic) need photo upload first because a no-website restaurant has no photos, so Editorial first (type-led) and Cinematic later; fixed UI labels only, never invented copy (the sample blueprint had "Secure Seating" and an invented tagline); tokens separate from structure; do not build the general engine from one vertical.
  - **Order:** 1) stage two real run and the Bayleaf conversation. 2) A refactor with no visible change inside the restaurant pack: the page becomes a list and a renderer with only today variants; tests prove identical output. 3) Editorial as the first added variant, offered by Scout as a choice in the plan card. 4) Salon pack on top, then extract the shared layer (one source packs import, instead of per-pack reference copies that drift).
- **Core pack.** Shared parts every vertical needs: owner sign-in (scrypt hashes, no `$`), rate limits in the database, env checks that stop the app, image storage adapter, CSV safety, alt text, claims log, demo notice, fault-injection switch.
- **Pack-aware wording.** The builder's instructions say "store" and "shopper." Take the nouns from the pack.
- **Cloud worker.** A container per run with a real sandbox, only that run's secrets, limited network and a time limit. Then a concierge beta, then self-serve.
- **Deploy step (built, `npm run deploy`, proven on Ksandra).** Neon through its API, Vercel CLI straight from the folder, subdomain on appnomics.live, `--set-password`, `--redeploy [--skip-migrate]`. Learned: Vercel production settings are sensitive and cannot be pulled back, so the script keeps the Neon project id and asks Neon for the address; the app's own commands run without tokens. Still open: variable names are hard-coded for the site pack (ADMIN_EMAIL, ADMIN_PASSWORD_HASH, SESSION_SECRET), so the store packs need their names mapped or the core pack must fix them; Blob store creation is still a dashboard step; verification does not sign in.
- **A delete tool and a `rm` allowance** for the agent (leftover helper files).
- **Trim the log and add a short store map** once a store has had about ten changes, so each change stays fast.
- **Time breakdown script.** Split a run into time waiting on the model and time between calls.
